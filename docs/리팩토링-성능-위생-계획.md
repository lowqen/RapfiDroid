> **읽는 법.** 2026-10-29 에 세운 계획서다. 목표는 엔진 분석 중 Compose 재구성 · 메인 스레드 연산 · 엔진

## 절대 규칙 — 어기면 그 커밋을 되돌린다

1. **화면 변화 0.** 레이아웃 · 여백 · 곡률 · 색 · 폰트 어느 1 px 도 달라지지 않는다. `-Pscreenshots=verify`
   (CI `screenshots.yml`, 골든은 CI 에서만 유효 — 로컬 폰트 래스터는 다르다)와 `ThemeContrastTest` 가 diff 0 으로 녹색.
2. **기능 회귀 0.** 엔진 프로세스 통신 · 온디바이스 수읽기 스트리밍 · 탭 좌표 · 기보 I/O · ViewModel 이
   화면에 내주는 계약을 지킨다.
3. **Phase 마다 승인.** 한 Phase 가 끝나면 측정과 CI 결과를 보고하고 다음 Phase 의 승인을 받는다.

## 진단 — 어디서 무게가 나오나

1. **병목은 Compose 앞단이다.** 엔진이 상태를 바꾸는 줄 하나마다 `SearchAggregator.snapshot()` 이 pvs · tags ·
   candidates · loseCells 넷을 통째로 복사하고, `BoardViewModel.uiState` 의 `combine` 이 `BoardUiState` 를 처음부터
   다시 짓는다. 그 안에 수와 무관한 일 — 오프닝 이름 4수 재분류, `openingGrade` 의 `PosKey`(대칭 8가지),
   `positionString`, `MoveGrader` 전 기보 재채점, `FontSpec.parse` 2회, `TagPalette` 생성 — 이 섞여 있다.
   `analyze()` 의 `channelFlow` 가 `viewModelScope` 에서 수집되므로 이 모두가 **메인 스레드**다.
2. **`BoardScreen` 이 맨 위에서 `ui` 전체를 읽는다.** `PositionCard` · `AnalysisCard` · `GameCard` · `MoveToolbar` ·
   `SummaryStrip` 등 17곳이 `ui: BoardUiState` 를 받으니 틱마다 화면 전체가 재구성되고,
   `ui.render.copy(provePulse = …)` 가 재구성마다 새 객체라 판도 매번 다시 그린다. 대국 시계(`GameRepositoryImpl`
   250 ms 틱)도 `game.state` 로 와서 대국 중 초당 4회 화면 전체가 재구성된다.
3. **Kotlin 2.4 는 strong skipping 이 기본이다.** 불안정 파라미터도 `===` 로 건너뛴다. 그러니 `@Immutable`
   일괄 부착보다 **상태를 쪼개 필요한 조각만 넘기는 것**이 핵심이다. 스크롤 오프셋을 컴포지션에서 읽는 곳은
   사실상 없고(`WhatsNew` 의 `canScrollForward` 하나, 이미 파생 상태), 람다 Modifier 로 바꿀 곳은
   `Segmented.kt` 의 `.offset(x = 애니메이션 값)` 하나다.
4. **판 그리기의 할당.** `drawValueText` · 돌 번호가 라벨마다 `android.graphics.Paint()` 를 새로 만들고
   `fontVariationSettings` 를 두 번 건다(typeface 파생 비용).
5. **안전망의 빈칸.** 골든 86장 중 Review · Rankings · Database · Explorer · Joseki · Prove · Tools · Connection
   화면은 0장, `AnalysisCard` 는 빈 상태만, `BoardViewModel` 테스트는 0개.

## 발견 사항 (리팩토링 범위 밖 — 화면을 바꾸므로 여기서 고치지 않는다)

- **굵은 값 라벨의 굵기**: 판 위 W/L(메이트) · DB 승/패 라벨은 850 으로 그리려던 것이지만, 라벨마다 굵기를
