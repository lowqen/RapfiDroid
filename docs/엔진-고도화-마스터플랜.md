## 0. 전제 교정 — 계획 전에 바로잡은 것

| 흔한 전제 | 실제 | 계획에 미치는 영향 |
|---|---|---|
| Kotlin ↔ C++ 사이에 **JNI 브릿지**가 있다 | 없다. `libengine.so` 는 **자식 프로세스로 실행하는 PIE 실행 파일**이고 stdin/stdout(piskvork)으로 말한다. 이유 4가지는 README 에 있다 — TT 할당 실패 시 `exit`, `chdir`, 탐색 취소, **GPL-3.0 ↔ BSD-2 경계** | JNI 전환은 **기각**(§2-4) |
| RapfiWeb 은 탐색 알고리즘까지 극한 튜닝됐다 | RapfiWeb 에서 **채택된 엔진 변경은 P2-2 · A1 · P4-1 · A3 넷뿐**이다. 탐색 쪽은 **모두 불채택** — P3-1 축소 완화 −6.7 Elo, P3-3 정책 생략 −19.4 Elo, P3-4 깊이 분산, P2-4 TT 쓰기, N1 소형 헤드 | 옮길 것은 「탐색 튜닝」이 아니라 **SIMD 커널 · 기동/스레드 운영 · 측정 규율** |
| 락리스 TT 를 검토해야 한다 | Rapfi TT 는 이미 xor 검증 무잠금이고 시간 몫 **0.26%**(RapfiWeb P1 프로파일) | 손대지 않는다 |
| RapfiDroid 가 RapfiWeb 보다 느리다 | 같은 기기에서 절대 NPS 는 네이티브 NEON 이 WASM 보다 높을 공산이 크다(x86 에서 WASM 은 SSE 의 43 ~ 56%). 진짜 격차는 **배운 것을 아직 하나도 안 가져왔다**는 것 | §1 |

## 1. 현재 엔진 분석 — 격차

**탑재본**(`app/src/main/jniLibs/ENGINE_VERSION.txt`):

- upstream `3c94c2a9` + **패치 0개**(안드로이드 빌드 패치 2개뿐), `USE_NEON=ON` · **`USE_NEON_DOTPROD=OFF`** · LTO, BENCH `e240ab16`.
- 빌드 스크립트가 dotprod 판(`libengine_dotprod.so`)도 만들지만 **「측정용」으로만 남기고 탑재하지 않았다.** 그 측정 기록도 없었다.
- 빌드 스크립트가 upstream **HEAD 를 클론**한다(커밋 고정 없음) — 다음 빌드가 다른 소스가 될 수 있다.
- 앱: 스레드 기본 3 · 해시 128MB(최대 512) · DB 켬. 기동 예열 없음, 발열 · 메모리 신호 처리 없음, FGS 타입 `dataSync`.

**ARM 핫패스**(upstream `vec.h` 를 직접 읽음):

| 연산 | 지금(NEON) | 가능한 것 | 비고 |
|---|---|---|---|
| i8 내적 `dot4_u7i8_accum`(값 헤드 starBlock — 네이티브 Ir 의 **46%**, RapfiWeb M1) | `vmull_s8` + `vmull_high_s8` + `vpaddq_s16` + `vpadalq_s16` = **4명령 / 16 MAC** | `vdotq_s32` **1명령** | WASM simd128 → relaxed(8 → 1)와 같은 구조 — 웹에서 **+18 ~ 57%** |
| `mulhi`(누산기 dwconv — Ir 의 31%) | `vmull_s16` + `vmull_high_s16` + `vuzp2q_s16` = **3명령** | `vqdmulhq_s16` **1명령** | x86 은 이미 1명령이라 A1 의 속도 이득이 0 이었다. **ARM 은 WASM 과 같은 처지** |
| starBlock 가중치 재사용(A3) | 미적용 | 입력 4개 배치 | 패치 주석의 「네이티브 효과 없음」은 **x86 이 로드를 `pmaddubsw` 에 접기 때문**. AArch64 는 load/store 구조 · 벡터 레지스터 32개라 그 논리가 성립하지 않는다 |

**결과 불변 A1 — 정확한 등가.** upstream 은 `mulhi(w, 4f) = ⌊4wf / 2¹⁶⌋` 를 계산한다(`slli<2>` 뒤 `mulhi`). NEON
`vqdmulhq_s16(w, 2f) = ⌊2 · w · 2f / 2¹⁶⌋` 는 **비트까지 같은 값**이다. 포화는 두 입력이 모두 INT16_MIN 일 때뿐인데
`2f ≥ 0` 이다. 그러므로 RapfiWeb A1 처럼 반올림을 바꿀 필요가 없다 — 웹 A1 의 정확도 비용(네이티브 추정 −8.8 Elo) 없이
3명령 → 1명령을 얻고, **BENCH `e240ab16`, 즉 PC · 서버와 같은 트리를 지킨다**(`MobileEngineConfig` 의 「폰 분석 = PC 분석」
원칙). 게이트는 해시 하나다 — 단 `f ≤ 8191` 을 넘는 병적 입력에서 upstream 의 `slli<2>` 랩어라운드와 갈릴 수 있으므로
BENCH · 묶음 해시로 확인한다.

## 2. 핵심 아키텍처 개편안

### 2-1. 바이너리 — 기기별 변형을 런타임에 고른다

- `libengine.so`(NEON) + `libengine_dotprod.so`(ARMv8.2+)를 jniLibs 에 함께 싣는다(각 ~1.5MB).
- `LocalEngineInstaller` 가 `/proc/cpuinfo` 의 `asimddp` 로 실행 파일을 고르고, dotprod 판이 **SIGILL(종료 코드 132)** 이면
  NEON 으로 후퇴한 뒤 그 결정을 기억한다.
- (실험) ARMv8.6 `i8mm` 판 — `smmla`(2×2 타일, 명령당 32 MAC)는 A3 배치와 잘 맞는다.
- 빌드 규칙: upstream 을 `3c94c2a9` 로 **고정**, RapfiWeb 처럼 `RAPFI_PATCHES` 목록을 `git apply`, 변형마다 BENCH 해시 게이트.

### 2-2. 스레드 모델 — big.LITTLE · 발열

- **기본 스레드 = 코어 구성으로.** `/sys/devices/system/cpu/cpu*/cpu_capacity` 로 리틀(최대의 50% 미만)을 뺀 수(예: 1+3+4 → 4).
  확정은 D4 측정 뒤.
- **발열 거버너(앱 쪽).** `PowerManager` 열 상태 리스너(API 29) · `getThermalHeadroom`(API 30) — MODERATE 이상이면 다음 탐색
  경계에서 스레드 한 단계 감소, SEVERE 면 무한 분석 일시정지 · 안내. 절전 모드는 2 스레드. 무한 분석은 「중지 → 스레드 변경 →
  재개」(TT 가 남아 손실이 작다).
- **P2-2 이식** — 스레드 변경 때 가중치 재적재 0. 거버너를 싸게 만드는 전제다.
- 메인 스레드 프라임 코어 고정은 **실험** — EAS 가 이미 잘 놓는지부터 잰다.
- **Lazy SMP 자체는 고치지 않는다.** RapfiWeb S1 에서 4 물리 코어 NPS 가 2 스레드의 ×2.1 — 남은 문제는 경합이 아니라 「같은
  일을 나누는 방식」이고, 그 답은 §2-5 S2 다.

### 2-3. 메모리 · OOM 방어

- **RAM 계층별 기본값**(`ActivityManager.MemoryInfo.totalMem` · `isLowRamDevice`):

  | RAM | TT | 스레드 상한 |
  |---|---|---|
  | ≤ 4GB | 64MB | 2 |
  | 6 ~ 8GB | 128 ~ 256MB | — |
  | ≥ 12GB | 512MB | — |

- **엔진 SIGKILL(137) 감지 → 다음 기동에 계층 한 단계 낮춤**(적응형).
- `onTrimMemory` 는 Android 14 부터 `RUNNING_*` 이 오지 않는다 — `UI_HIDDEN` / `BACKGROUND` 에서 대기 중이면 `YXSAVEDATABASE`.
- yixindb 는 통째로 메모리에 있다 — 크기 표시 · 상한 경고.
- **실기 검증할 위험**: Android 12+ PhantomProcessKiller(앱의 자식 프로세스 감시)가 백그라운드 분석 중 엔진을 죽이는지,
  백그라운드에서 엔진 자식 프로세스의 cpuset 이 리틀로 밀리는지 — `/proc/<pid>/cpuset` 으로 시험한 뒤 대응을 정한다.
- **FGS 타입**: `dataSync` 는 targetSdk 35(Android 15)에서 **하루 6시간 한도 · `onTimeout`** 이 있다 — 긴 분석에는
  `specialUse` 가 맞다(배포가 F-Droid 라 심사 부담 없음).

### 2-4. 프로세스 경계 — 기각과 소폭 개선

- **JNI 전환 기각**: RapfiWeb 에서 출력 경로는 병목이 아님을 두 번 확인했다(O1 기각 · P2-5 불채택 — ~70줄/초). 파이프는
  줄당 마이크로초 단위이고, JNI 는 GPL 경계 · `exit` 크래시 · `chdir` 문제를 되살린다.
- 대신 **기동 예열**: 지금은 첫 ▶ 에서 가중치 lz4 해제(폰에서 1초 이상 추정)를 사용자가 기다린다. START 직후 노드 제한 짧은
  탐색으로 미리 푼다(RapfiWeb P1-1 과 같은 교훈).
- 장시간 분석의 출력 빈도 조절은 **측정에서 비용이 보일 때만.**

### 2-5. 수읽기 — 장기 과제 하나

- **S2 VCT(df-pn) 증명 보조 스레드.** Rapfi 에 VCT 전용 솔버가 없고(RapfiWeb 1부 H2), +M43 누락의 원인도 「본 탐색이 긴
  VCT 를 늦게 연다」였다. 폰 4코어 이상에서는 Lazy SMP 복제 스레드 하나를 증명기로 돌리는 것이 한계 가치가 가장 크다.
- C++ 소스가 같으므로 **RapfiWeb 과 공동 개발**, 판정은 네이티브 ARM 의 60 ~ 180초 하드 묶음 + SPRT.

## 5. 판정 규칙 (RapfiWeb v2 §7 을 따른다)

1. **결과 불변 변경**: 해시 일치 + D2 명령 수 감소 + D1 에서 A/A 가 0 을 품고 시험 구간 하한 > 0 — **두 번 연속.**
2. **트리를 바꾸는 변경**: 주 지표는 **SPRT 하나.** 노드비 · NPS 는 참고.
3. **ISA 마다 속도가 다른 변경은 실제 ARM 에서 판정** — RapfiWeb A1 이 x86 네이티브로 판정했다가 틀린 교훈.
4. 중단 조건을 착수 전에 표에 적고, 관문을 못 넘으면 다음 단계(특히 SPRT)를 돌리지 않는다.
5. 폰 측정은 **식힌 뒤 · 코어 군 고정 · 순서 번갈음**. 열 상태가 다른 두 측정은 비교하지 않는다.
6. **ARM CI(`arm-bench.yml` `mode=speed`)의 1번 규칙은 이렇게 읽는다**(2026-10-27 채택, 같은 날 0.5% → **1.0%** 로 고침): A/A 점추정 |x| ≤ 1.0%
   이고, 시험 구간 하한이 A/A 구간 끝 가운데 절댓값이 큰 쪽보다 크다 — **두 런 연속.** 이 러너는 짝 로그 sd 가 ~0.01 로 작아 구간이 프로세스마다의
   바닥(±1%, 부호가 런마다 바뀜)보다 좁다. 「A/A 가 0 을 품는다」를 그대로 쓰면 하네스가 멀쩡해도 거의 늘 못 넘는다(D3 · K5 절). 처음의 0.5% 는 코어
   고정 뒤 A/A 여덟 쌍(그중 넷은 ASLR 끄기까지) 가운데 넷이 넘어(최대 0.91%) 1.0% 로 넓혔다. **효과 1.5% 미만은 이 러너로 판정하지 않는다.**

**방법.** dotprod 엔진(K1 전), TT 128MB, 렌주, 국면 3개(open-direct · open-indirect · midgame) × 10초, 탐색마다 해시 비움. 스레드 순서
**4 → 6 → 8 → 8 → 6 → 4**(열 치우침 상쇄), 실행 사이 90초 쉼. 배터리 34.7 ~ 35.0 ℃(따뜻한 상태에서 출발 — 셋 모두 같은 조건).

| 스레드 | open-direct | open-indirect | midgame | 기하 평균 | 4 대비 | A55 평균 클럭 |
|---|---|---|---|---|---|---|
| 4 | 172K · 168K | 121K · 112K | 214K · 212K | **162K** | ×1.00 | 1.64 ~ 1.72GHz |
| 6 | 217K · 191K | 146K · 149K | 267K · 272K | **201K** | **×1.24** | 1.64 ~ 1.75GHz |
| 8 | 255K · 240K | 189K · 180K | 323K · 412K | **255K** | **×1.58** | **1.95GHz** |

- 4 스레드 162K 는 D4 A4(163K)와 같다 — 측정이 재현된다.
- **6 → 8 이 4 → 6 보다 더 오른다**(×1.27). A55 6개가 다 바쁘면 그 클러스터가 1.95GHz 까지 오르고(4 · 6 스레드에서는 ~1.65GHz),

- **NPS ≠ 실효 강도.** 같은 15초에 도달한 깊이는 8 스레드가 4 스레드보다 깊지 않았다(midgame d25 · d25 ↔ d21 · d19) — Lazy SMP 는
  스레드가 늘면 축소(LMR `0.1·ln n`)와 중복 탐색도 는다. 「8 이 더 강하다」는 SPRT 로만 확정된다(D3 이후).

**조치.**

- 앱 상한은 이미 `MAX_THREADS = 8` 이었고 설정 칩에 8 이 있었다 — 그대로 둔다. 대신 칩 목록을 `LocalEngineProfile.THREAD_CHOICES`

  않았다). 단위 테스트: 6 · 8 · 최댓값이 선택지에 있고, 8 을 고르면 `clamp` 를 지나도 8 이 엔진까지 간다.

  「|A/A| ≤ 0.5%」로는 네 런 중 둘이 무효다. 기준을 ±1% 로 넓히거나(그러면 1.5% 미만 효과는 판정하지 않는다), 남은 프로세스 차를 더 줄여야 한다 —
  다음 시도 후보는 엔진을 `setarch -R`(ASLR 끄기)로 띄워 프로세스마다의 메모리 배치를 같게 하는 것.
