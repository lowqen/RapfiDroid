# 보안 강화 계획 — 무엇을 지키고, 어디가 실제로 뚫리나

> **읽는 법.** 2026-10-31 에 세운 계획서다. 아직 코드는 한 줄도 바꾸지 않았다 — 이 문서는 조사 결과와
> Phase 별 작업 목록이고, Phase 마다 승인을 받고 진행한다. 근거는 모두 `파일:줄` 또는 GitHub API 조회 결과로 적었다.

## 먼저 정직하게 — «어떤 해커도 못 뚫는 앱» 은 없다

절대적인 보안은 어떤 앱에도 없다. 그래서 이 계획은 **«무엇을 지키는가»** 를 먼저 정하고, 거기에 닿는 길을
하나씩 막는다. 그리고 Zenyth 는 일반적인 앱과 지켜야 할 것이 다르다.

- 계정 · 결제 · 서버 · 개인정보가 **없다**(README: «No server. No account.»). 폰 안에 훔쳐 갈 비밀이 사실상 없다.
- 소스가 **GPL 로 공개**돼 있다. 공격자는 디컴파일할 필요도 없이 소스를 읽는다.

그러니 공격자가 노릴 만한 것은 «폰 속 데이터» 가 아니라 아래 넷이다. 계획도 이 순서로 무게를 둔다.

| # | 지킬 것 | 뚫리면 |
|---|---|---|
| **A1** | **배포 경로** — 서명 키 · GitHub 계정 · CI · 릴리스 | 악성 업데이트가 **모든 사용자**에게 정상 업데이트처럼 깔린다. 가장 치명적 |
| **A2** | **앱이 받는 입력** — 딥링크 · 고른 파일 · 커리큘럼 JSON · 클립보드 · 서버 엔진 응답 | 앱 강제 종료(DoS) → 최악은 파서 버그를 통한 오동작 |
| **A3** | **사용자 자신의 엔진 서버**(Tailscale, TCP 5050) | tailnet 안의 다른 기기가 서버 엔진을 마음대로 사용 |
| **A4** | 폰 속 데이터 — 기보 · DB · 설정 · 디버그 로그 | 민감도 낮음. 백업 · 외부 저장소 경로만 정리 |

## 하지 않을 것 — 그리고 왜

흔히 «앱 보안» 하면 떠오르는 것들이지만, 이 앱에서는 **이득이 없거나 해롭다.**

| 하지 않을 것 | 이유 |
|---|---|
| 코드 난독화(R8 obfuscation · DexGuard) | 소스가 공개라 숨길 것이 없다. 크래시 스택을 매핑 없이 읽는 지금 설정(`proguard-rules.pro`)을 깨고, 엔진 패키지 keep 규칙과도 부딪힌다 |
| 루팅 · 에뮬레이터 탐지, 안티 디버깅, 무결성 자가 검사, Play Integrity | 지킬 서버 · 계정 · 결제가 없다. 자기 폰을 루팅한 사용자를 막을 이유도 없다. F-Droid 는 자체 키로 다시 서명하므로 서명 자가 검사는 F-Droid 판을 망가뜨린다 |
| 인증서 피닝(curriculum) | Cloudflare 인증서가 회전하면 앱이 커리큘럼을 못 받는다. 무결성은 S9 의 **내용 서명**이 더 정확하고 안전하다 |
| 서버 엔진 TLS · 인증 추가, 엔진 응답 파서 길이 제한, 엔진 빌드 플래그(FORTIFY 등) 변경 | **엔진 불가침 규칙**(엔진 파일 · 통신 · 엔진이 받는 값과 시점)에 닿는다. 엔진 바이너리는 이미 PIE · RELRO · NX · 스택 보호가 켜져 있다. 서버 쪽은 Tailscale ACL 로 막는다(Phase 5) |
| 엔진 명령 경로(`hashdump` · `reloadconfig` 등)의 입력 필터링 | 같은 이유. 엔진은 앱 샌드박스 안에서만 파일을 쓸 수 있어 피해 범위도 앱 자신뿐이다 |

## Phase 0 결과 (2026-10-31)

`gh api` 로 만들고 다시 조회해 확인한 상태다.

| 설정 | 내용 |
|---|---|
| Ruleset `main: no force-push or delete` (26218678) | 기본 브랜치의 강제 push · 삭제 금지. 우회 없음(관리자 포함). 일반 push 는 그대로 |
| Ruleset `release tags: create by admin only` (26218680) | `refs/tags/v*` 생성은 저장소 관리자만(우회 = RepositoryRole admin). `GITHUB_TOKEN` · Dependabot · 앱 · 협업자는 릴리스 태그를 만들 수 없다 |
| Ruleset `release tags: immutable` (26218682) | 이미 있는 `v*` 태그의 이동 · 삭제 금지. 우회 없음 — 낸 릴리스가 가리키는 커밋은 바뀌지 않는다 |
| Environment `release` | 배포 전 `lowqen` 승인 필수, 허용 ref 는 태그 `v*` 와 브랜치 `main` 뿐 |
| Private vulnerability reporting (Zenyth) | 켜짐 |
| `Zenyth-web` secret scanning · push protection | 켜짐 |

**아직 효력이 없는 부분.** `release.yml` 이 아직 `environment: release` 를 선언하지 않았고 서명 시크릿 4개도 저장소
레벨에 있다. Environment 의 승인 단계는 **Phase 1** 에서 워크플로에 연결하고, 그때 사용자가 시크릿을
`gh secret set <이름> --env release --repo lowqen/Zenyth` 로 다시 등록한 뒤 저장소 레벨 시크릿을 지운다 — 순서가
바뀌면 릴리스가 깨진다.

**한계.** 관리자 권한이 있는 **본인 토큰**이 새면 태그 생성 규칙은 우회되고, 배포 승인도 API 로 할 수 있다.
그래서 계정 2FA(패스키 · 하드웨어 키)와 토큰 정리가 이 설정들보다 앞선다 — 그 둘은 사용자 몫으로 남아 있다.

**사용자 몫(남음).** 2FA 를 패스키 · 하드웨어 키로, 쓰지 않는 토큰 폐기, Cloudflare 계정 2FA, 서명 키스토어
암호화 오프라인 백업 두 곳.

### 함께 한 CI 속도 정리

| 바꾼 것 | 왜 |
|---|---|
| `build.yml`: 문서(`docs/**` · `*.md` · `fdroid/**`)만 바뀐 push 는 빌드하지 않는다 | 이 작업에서 문서 커밋마다 6분짜리 빌드가 돌았다 |
| `build.yml` · `screenshots.yml`: 같은 브랜치의 새 push 가 오면 진행 중인 실행을 취소(`concurrency`) | 연달아 push 할 때 낡은 실행이 러너를 잡고 있었다 |
| 러너 크기에 맞춘 Gradle 설정(힙 4 GB · 작업자 4) — `release.yml` 은 이미 그랬다 | `gradle.properties` 는 4 GB 노트북용(힙 1.25 GB · 작업자 2)이라 R8 이 GC 에 시간을 썼다 |
| `build.yml`: 테스트 · debug · release(R8)를 Gradle 한 번에, configuration cache 로 나란히 | 설정 · 컴파일을 한 번만 하고, 테스트(135 s)와 R8(169 s)이 서로 기다리지 않는다 |
| `build.yml` 은 스크린샷 두 클래스를 빼고(`-PskipScreenshotTests`) `screenshots.yml` 에 맡긴다, 테스트는 JVM 2개(`-PtestForks=2`) | 같은 골든을 두 워크플로가 매번 그렸다. 두 속성 모두 CI 에서만 — 평소 빌드는 그대로 |
| 디버그 아티팩트 이름 `Zenyth-<버전>-debug-<커밋>`, 보관 14일 | 전부 `app-debug` 라 어느 빌드인지 알 수 없었다. 내용은 늘 그 커밋의 0.16.0 이었고, 59.6 MB 는 R8 없는 debug 의 dex(20.9 MB) 때문이다(서명 릴리스는 46 MB) |

왔으므로, 코드를 바꾼 push 에서는 debug job 이 더 길다 — 그래도 release job(약 4 분)보다 짧아 벽시계는 약 4 분.
